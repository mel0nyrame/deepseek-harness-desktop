# Agent Note: 退役仓库自动化工作流

Status: implemented

[English](2026-08-15-retire-repository-automation-workflows.md) | 中文

## 问题

若干 GitHub Actions 通道重复执行仍可通过仓库命令完成的操作、使用外部凭据，或自动投影 Issue 状态。即使仓库不再要求远程执行这些操作，保留这些通道仍会让 GitHub 配置成为额外的执行面和凭据面。

## 决策

GitHub Actions 保留可复用的 Python 运行时构建器、Issue 策略、CI、文档页面、沙箱、Landlock CI，以及手动触发的 E2B 集成测试。独立的真实 API provider 测试、包发布、预期文件名检查和 Issue 生命周期投影通道均不再存在。

发布准备、验证、打包和发布仍由仓库内的本地命令负责。Landlock 发布要求先在各受支持架构上进行原生构建，再把产物传入一个干净 checkout，随后运行现有的汇总、验证、打包、安装副本验证和注册表感知发布脚本。Python 运行时 wheel 构建仍可通过可复用构建器和 GitLab CI 使用，但 GitHub 不再汇总或发布公开 Python 候选发行版。Issue 生命周期处理器及其单元测试仍作为源码能力保留，但不再有 GitHub 事件订阅方。

## 考虑过的替代方案

**保留不常运行的手动工作流。** 手动触发仍会保留凭据、配置和维护面；仅仅不运行并不能简化仓库自动化。

**把被移除的发布通道并入主 CI 工作流。** 这会把无凭据的 PR 检查与受保护发布和外部服务操作混在一起，而不是移除远程执行面。

**连同工作流一起删除底层脚本和测试。** 本地发布命令、可复用运行时构建器和 Issue 管理逻辑仍可脱离 GitHub 事件接线独立使用。

## 后果

GitHub 不再定时或手动触发被移除的操作。维护者需要在已认证的本地环境中运行发布流程，并负责保留原生架构来源以及在发布前检查本地产物。真实 API 覆盖改为本地执行，不再是 GitHub 合并信号；Issue 状态投影也不再自动运行。

保留的工作流继续覆盖 PR CI、文档、沙箱行为、Landlock 原生构建、供调用方使用的 Python 运行时构建、Issue 策略，以及显式触发的 E2B 在线集成通道。重新引入被移除的通道时，必须存在当前的远程执行需求，并明确触发与凭据模型，还要为其失败模式提供聚焦测试；本地命令能够提供同等能力时仍是默认选择。

本决策整合了此前专用的 DeepSeek 真实 API CI 和 Python 发布决策。它们的原始目标——发现无密钥测试无法暴露的集成故障，以及发布一组经过验证的多 wheel 包——仍然有效，但已不足以证明保留携带 secret 或具备发布能力的 GitHub 工作流是合理的。本地真实 API 运行以及保留的构建和发布脚本可在不进行远程调度的情况下保留这些能力。

未来任何携带 secret 的 PR 通道都必须使用 `pull_request`，绝不能使用 `pull_request_target`；它必须依靠 GitHub 对 fork 和 Dependabot 隐藏 secret，并在预期 secret 缺失时先失败，避免自动跳过的测试套件产生虚假绿色结果。为可信的同仓库 PR 启用该通道意味着接受有写权限的贡献者可用仓库 secret 执行代码；省略该触发器会缩小暴露面，但同时放弃合并前的真实服务信号。

未来任何 Python 发布通道都必须只发布经过检查的原始 wheel 字节，在上传前验证保留的哈希，先发布全部运行时 wheel，再发布精确依赖它们的 SDK，并将发布作业分开，使 SDK 重试绝不替换不可变的运行时文件。Trusted Publishing 身份包含仓库、工作流和环境；其中任一项变化都必须同步更新 PyPI publisher。改用 token 会重新引入可复用 secret 及其轮换负担。

未来任何 Issue 生命周期订阅方都必须保留事件命令模型：重复请求评审将目标设为 `In review`，请求修改的评审将目标设为 `In progress`，唯一允许的回退转换必须先确认最新 Project 状态归自动化所有。批准、评论和撤销评审不得产生生命周期变更。保留处理器但不配置事件订阅方是有意选择；重新引入自动投影时，除了处理器测试外，还必须恢复聚焦的工作流事件覆盖。
